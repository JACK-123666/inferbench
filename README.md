**一句话目的**：给本地 / 私有化 LLM 部署做**选型与容量决策**的测量台。
它回答的不是「模型聪不聪明」，而是「这台 8GB 卡上：用哪个量化档、缓存阈值定多少、
能扛几路并发、每一项的代价是什么」—— 把选型从凭经验拍，变成有数字、能复现、敢报负结果。

**三条最硬的证据**（都是这台装置自己测出来的，不是引用别人的）：

1. **纯推理不该留 FP16**：Q8 准确率（92.0%）不低于 FP16（91.0%），同时省 39% 显存、快 57%
   —— 「精度越高越好」是直觉陷阱，FP16 只在还要继续训练 / 微调时才需要。
2. **缓存阈值不是质量杠杆**：0.80 → 0.98，误命中率反而 15.9% → 18.1%。拆解归因后发现
   **100% 是「缓存把后端模型当初答错的那一次固化了」**，跨意图误匹配 0 次 —— 该做的不是调阈值。
3. **加并发不换吞吐，只换排队**：并发 1→8，QPS 只涨 6%，TTFT P95 涨 69 倍；根因是
   `OLLAMA_NUM_PARALLEL=1` 单 slot 串行 —— 只改这一个配置，吞吐 2.5×、TTFT 降 24×，代价显存 +86%。

**它不是什么**：不是训练 / 微调工具（SFT、DPO 不做），不是跑分榜单，
不是部署框架（K8s、多机推理不在范围内）。

> 📖 **第一次接触？先看 [`TUTORIAL.md`](TUTORIAL.md)** —— 零基础教程（v2 完整版）：
> 12 章 + 4 个附录，从"量化是什么"讲到"怎么把结论讲清楚"，
> 含 19 个概念的四段式讲解、三个实验的手把手流程、8 类真实故障的排错手册、测量纪律检查清单。
> 赶时间就看 **附录 D 三分钟速览**。

整套实验跑在**本地 Ollama + RTX 4060 8GB** 上；工程零第三方依赖（只用 Python 标准库），克隆下来就能跑。

## 1. 结论先给：每个决策的答案

| 你要做的决策 | 实测答案 | 出处 |
|---|---|---|
| 量化档位怎么选 | 纯推理用 **Q8**：准确率不劣于 FP16（92.0% vs 91.0%），省 39% 显存、快 57%。**Q4 是拐点**：整体掉 5pp，难例掉 **8.7pp** | §6 实验一 |
| 语义缓存阈值定多少 | **阈值不是杠杆**：0.80 → 0.98，误命中率 15.9% → 18.1%。正解是易错意图不进缓存 / 命中后二次校验 | §6 实验二 |
| 要不要给缓存加写入门槛 | **不要**（负结果）：98.7% 采样自洽，门槛只挡下 1 次写入，成本从省 42% 变**亏 75%** | §6 实验三 |
| 投机解码值不值得上 | 草稿模型**不值**（0.50–0.71×，草稿成本占 target 的 35%）；零成本 **n-gram 草稿值**（1.83×） | §6 实验四 |
| 一个实例能扛几路并发 | 默认**只 1 路**（要 TTFT P95 < 200ms）；`OLLAMA_NUM_PARALLEL=4` 后吞吐 2.5×、TTFT 降 24×，代价显存 +86% | §6 实验五 |

以上每条都有 CSV 明细与 Markdown 报告可溯源（`results/`），结论句由脚本从结果文件生成，不手抄。

### 实验索引（怎么跑出这些答案）

| 实验 | 回答的问题 | 产出 |
|---|---|---|
| `inferbench quant` | 同一模型 FP16/Q8/Q4 各档，**显存、吞吐、准确率**三者怎么换？ | 三角表 + 折线/柱状 SVG + 分层部署选型结论 |
| `inferbench cache` | 语义缓存阈值定多少？命中率、**误命中率**、端到端准确率、成本与 P95 的取舍？ | 阈值扫描表 + 灰度/回滚/多版本验证 |
| `inferbench gate` | 承接上一步的归因结论：给缓存写入加**自一致性门槛**，误命中能降下来吗？ | A/B 对照 + **负结果**（见 §6） |
| `inferbench spec` | 投机解码能快多少？草稿模型 vs n-gram 草稿，**接受率与加速比的关系**？ | 两类负载 × 6 配置 + 正确性对照（见 §6） |
| `inferbench load` | 单实例能扛多少并发？**吞吐上限与尾延迟拐点**在哪？ | 并发梯度 × QPS/TTFT/P95/P99（见 §6） |

设计上有两条硬规矩：
1. **每个结论都必须挂在一个客观评测基准上**（复用 Synapse 开源工程的 100 条人工标注意图集），
   不靠"感觉效果不错"。
2. **凡是没实测的东西，一律显式标注为"调研"**，不混进实测数字里。

## 2. 统一入口

所有功能都收敛到一个入口：**`python -m inferbench <命令>`**。

```powershell
python -m inferbench            # 不知道有什么命令？直接敲这个
```

| 命令 | 做什么 |
|---|---|
| `env` | 环境体检：显卡 / Ollama / 模型 / 依赖 / 测量口径 |
| `dataset` | **语料体检**：接自己的数据（格式 / 能测什么 / 标签对不对得上任务定义） |
| `quant` | 实验一 · 量化档位对比（显存↓ / 速度↑ / 精度↓） |
| `cache` | 实验二 · 语义缓存（阈值扫描 + 误命中归因） |
| `gate` | 实验三 · 缓存写入门槛（自一致性 A/B，负结果） |
| `spec` | 实验四 · 投机解码（draft 模型 vs n-gram） |
| `load` | 实验五 · 并发压测（QPS / 尾延迟 / 真实 TTFT） |
| `recommend` | **收敛 · 选型建议**：读 `results/*.json` 算出「本机该怎么配 + 代价」（不跑模型） |
| `report` | 用旧 JSON 重新生成报告（改了文案不用重跑实验） |
| `test` | 跑单元测试（pytest） |
| `models` | 列出模型及其对应的 GGUF 文件路径 |

**设计原则：CLI 只做路由，不塞业务逻辑。** 每个子命令背后都是
`inferbench/experiments/*.py` 里的 `run(argv) -> int`，所以这些实验也能被别的脚本 import 调用。
唯一的例外是 `recommend`（`inferbench/recommend.py`）：它是**收敛层** —— 不产生新数据，
只把已有结果算成决策，所以它没有「测量口径」这一说。

装成正经的包也可以：`pip install -e .` 之后，**任何目录**下都能用 `inferbench env`
（等价于 `python -m inferbench env`），也能 `from inferbench import cache, report` 当库用。

## 4. 快速开始

```powershell
cd D:\PYTHON\inferbench
pip install -r requirements.txt      # 只有实验五和测试需要装依赖

python -m inferbench env                    # ① 先体检：显卡够不够、模型装没装、依赖缺不缺

# ② 冒烟测试（12 条样本，约 30 秒）
python -m inferbench quant --limit 12 --repeats 1 --tag smoke

# ③ 实验一：完整量化阶梯（100 条 × 3 次重复 × 3 档，约 5 分钟）
python -m inferbench quant --models qwen3:1.7b-fp16,qwen3:1.7b-q8_0,qwen3:1.7b

# ④ 实验二：语义缓存（不调模型生成改写，最快）
python -m inferbench cache --perturb-only --thresholds 0.85,0.90,0.92,0.95

# ⑤ 实验五：并发压测（新）
python -m inferbench load --levels 1,2,4,8,16 --requests 24

# ⑥ 收敛：把上面的结果算成「本机该怎么配」（不跑模型，秒出）
python -m inferbench recommend --vram 8 --slo-ttft 200 --concurrency 4
```

### 用你自己的语料（不必依赖 Synapse）

先把文件喂给体检，它会告诉你**能测什么、不能测什么**：

```powershell
python -m inferbench dataset raw_queries.txt              # 一行一条 prompt 也能读
python -m inferbench dataset q.csv --text-col question --intent-col category
python -m inferbench dataset my.jsonl --write data/my_corpus.jsonl   # 规范化后直接用
```

然后交给实验（量化 / 缓存 / 门槛 / 并发都支持 `--eval-set`）：

```powershell
python -m inferbench quant --eval-set data/my_corpus.jsonl --models qwen3:1.7b-q8_0
```

格式是 jsonl，一行一条：`{"text": "...", "intent": "...", "hard": false}`（后两个字段可省）。
PowerShell / 记事本存出来的带 BOM 文件也能读。

**两个必须先知道的限制**（`dataset` 会替你检查，并写进报告）：

1. **没有标签就测不出准确率** —— 只能测吞吐与延迟。量化实验会**直接拒绝运行**，
   而不是给你一个恒为 0 的准确率。
2. **换标签必须同时改任务定义** —— 标签不在 `inferbench/tasks.py` 的 `LABELS` 里时，
   准确率会恒为 0。**那不是模型不行，是尺子错了**；要换标签就同时改
   `LABELS` / `SYSTEM_PROMPT` / `FEW_SHOTS` / `SYNONYMS` 四处。

准确率类结论**只在它所用的那份语料上成立**，所以每份结果都会记下语料的来源、条数与
**内容指纹**（sha1 前 8 位），报告头部会印出来；`recommend` 一旦发现多份结果用了
不同语料，会直接告警——跨语料的准确率横向对比是不成立的。

跑完看 `results/` 下的 `.md`：除了表格和 SVG 图，最后一段是**可直接引用的结论**，
数字全部自动取自本次运行。

## 5. 测量口径（所有数字都按这一套产出）

| 项 | 取值 | 为什么 |
|---|---|---|
| `num_ctx` | 4096 | 默认 131072 会让 KV cache 吃满显存（本机实测 1.2GB ↔ 5.1GB），不锁死就变成"测显存" |
| `temperature` / `seed` | 0 / 42 | 降低采样随机性对准确率的影响 |
| `think` | False | Qwen3 等思维链模型必须关掉，否则输出混推理链，token 数不可比 |
| few-shot | 3（所有模型相同） | 保证对比公平 |
| 重复次数 | 3，取中位数并给 P95 | 单次测量抖动大 |
| 预热 | 1 次并丢弃 | 冷启动实测 14s，首调用 12 tok/s vs 预热后 168 tok/s |
| 显存隔离 | 每个模型测量前 `unload_all()` | 见 §7 踩坑记录 |

**每份结果都自带适用范围。** 落盘时自动采集一份环境指纹 —— GPU 型号 / 显存总量 / 驱动 / CUDA、
Ollama 版本与实际 host、`OLLAMA_NUM_PARALLEL`、Python 与 `inferbench+git` 版本 —— 写进结果的
`env` 块，并在报告开头印成「适用范围」段。理由很直接：**这里的每个结论都绑定硬件**，
「8GB 卡上草稿模型全负收益」换到 24GB 卡上就不成立，所以看任何一份旧结果之前，先看它的适用范围。

> 本仓库里的历史结果（`quant_ladder-*`、`cache_*`、`cache_gate_*`、`spec_full`、`load_*`）
> 产生在这个功能之前，报告会明确标注「适用边界未知」，而不是假装有指纹。
> `results/quant_owncorpus.*` 是用 `data/example_corpus.jsonl`（15 条手写样例）跑的一次小实验，
> 只为演示 `env` 块与语料指纹长什么样，**不是结论依据**。

## 6. 已跑出的结果（示例）

### 实验 1 · 完整量化阶梯（**同一模型** FP16 / Q8 / Q4，100 条 × 3 次重复，num_ctx=4096）

| 模型 | 显存 | 准确率 | 难例准确率 | 非法输出率 | TTFT 中位 | 解码 |
|---|---|---|---|---|---|---|
| `qwen3:1.7b-fp16` | 3.69 GB | 91.0% | 78.3% | 1.0% | 18.5 ms | 85.3 tok/s |
| `qwen3:1.7b-q8_0` | 2.24 GB | **92.0%** | 78.3% | 1.0% | 13.6 ms | 134.2 tok/s |
| `qwen3:1.7b` (Q4_K_M) | 1.59 GB | 87.0% | 69.6% | 0.0% | 10.7 ms | 191.6 tok/s |

三个关键结论：

1. **准确率不随精度单调变化**：Q8（92.0%）反而**高于** FP16（91.0%）。
   差值只有 3/300 条记录（噪声范围），但结论成立：**Q8 在本任务上不劣于 FP16，
   同时显存少 39.3%、吞吐高 57.4%、TTFT 低 26.4%**。
   → **FP16 在纯推理场景被完全支配**，只有要继续训练/微调（LoRA、DPO）时才需要保留。
   **「精度越高越好」是直觉陷阱。**
2. **Q4 才是真正的拐点**：相比 Q8，Q4 省 29% 显存、快 43%，但准确率掉 5pp、
   **模糊难例掉 8.7pp**（78.3% → 69.6%）。难例掉幅是整体掉幅的近 2 倍——
   **量化损伤优先暴露在难例上**，这也是评测集必须包含难例的原因。
3. **错误形态是分类混淆，不是格式崩溃**：主要错误是 `summarize → small_talk`（错 30 次），
   而且 Q4 的非法输出率（0.0%）反而比 Q8（1.0%）低。**量化先崩哪一环，必须看混淆矩阵。**

### 实验 1 补充 · 加入更小模型的对照（`qwen3:0.6b`）

| 模型 | 显存 | 准确率 | 难例准确率 | 非法输出率 | TTFT | 解码 |
|---|---|---|---|---|---|---|
| `qwen3:0.6b` | 0.87 GB | 54.0% | 47.8% | **13.0%** | 10.2 ms | 268.5 tok/s |

`qwen3:0.6b` 提供了**另一种失效模式**：它不是"答错题"，而是**13% 的概率不按格式答题**。
→ 这决定了工程处置方式完全不同：分类混淆要换模型/调 prompt，格式崩溃要加输出校验+重试。

### 实验 2 · 语义缓存（300 条请求 = 100 query × 3 种说法，231 条唯一文本）

| 阈值 | 命中率 | 误命中率 | A类·继承后端错误 | B类·跨意图误匹配 | 端到端准确率 | 无缓存基线 | 成本节省 |
|---|---|---|---|---|---|---|---|
| 0.80 | 60.7% | 15.9% | 29 | **0** | 85.3% | 86.0% | 60.4% |
| 0.92 | 42.3% | 14.2% | 18 | **0** | 86.0% | 86.0% | 42.0% |
| 0.98 | 27.7% | 18.1% | 15 | **0** | 85.7% | 86.0% | 27.2% |

三个关键发现：
1. **误命中率不随阈值下降**：0.80 时 15.9%，提到 0.98 仍是 18.1%。调高阈值只砍掉命中率，没砍掉错误。
2. **归因分解：A 类占 100%，B 类 0 次**。误命中的成因不是"阈值太松"，而是
   **缓存存的是后端模型当初的预测——模型答错的那一次被永久固化，之后所有语义相近的请求都被这个错答案命中**。
   阈值再高也救不了，因为它在写入缓存时就已经错了。
3. 因此**语义缓存不制造新错误，它只是原样传播后端模型的错误**：端到端准确率与无缓存基线（231 条唯一文本各真跑一次 LLM）**完全一致**（86.0%），
   而成本省了 42%。真正该做的不是继续调阈值，而是**高价值/易错意图不进缓存**或**命中后二次校验**。

### 实验 3 · 缓存写入门槛（自一致性）—— 一个干净的负结果

顺着上面的结论，给"写入缓存"加门槛：同一条 query 采样 3 次（temperature=0.7），**全部一致才允许写入**。
A/B 用同一张采样表，唯一变量是门槛开关：

| 指标 | 门槛关闭 | 门槛开启 |
|---|---|---|
| 命中率 | 42.3% | 41.7% |
| 误命中次数 | 18 | 16 |
| 缓存条目数 | 173 | 172 |
| 端到端准确率 | 86.3% | 86.7% |
| **成本节省** | **+42.4%** | **−74.7%** |
| 延迟中位数 | 89 ms | 165 ms |

**判定：门槛无效，不建议采用。**

- **根因在采样一致率：227/230 条文本（98.7%）采样 3 次结果完全一致**，门槛总共只挡住了 **1 次**写入。
- 也就是说这个小模型是**「稳定地错」而不是「随机地错」**——自一致性只在"模型自己会犹豫"时有效，
  对系统性偏差**在原理上就无效**。
- 代价却实实在在：**从省 42% 成本变成亏 75%**，延迟 1.8 倍。

这个负结果比正结果更有价值：它把「在缓存层加个门槛就好了」这条路排除了，
把改进方向钉死在**后端模型质量**和**意图级策略**上。

### 实验 4 · 投机解码（target=qwen3:1.7b，draft=qwen3:0.6b）

用 Ollama 自带的 llama-server（就是完整 llama.cpp 构建，**无需额外下载**）+ CUDA 后端，
两类负载各 6 条 prompt：

| 配置 | A-结构化抽取 | B-自由摘要 | 接受率 α (A/B) |
|---|---|---|---|
| `base`（基线） | 154.2 tok/s（1.00×） | 152.5 tok/s（1.00×） | — |
| `base2`（**重复性对照**） | 155.3（1.01×） | 152.2（1.00×） | — |
| `draft-k3` | 107.4（**0.70×**） | 100.2（0.66×） | 69.9% / 65.3% |
| `draft-k8` | 109.2（0.71×） | 94.8（0.62×） | 56.6% / 45.7% |
| `draft-k16` | 76.5（**0.50×**） | 57.3（0.38×） | 30.8% / 22.0% |
| **`ngram`**（无草稿模型） | **282.0（1.83×）** | **181.2（1.19×）** | **100% / 94.2%** |

四个反直觉结论：

1. **草稿模型方案在消费级显卡上全是负收益**（0.50×~0.71×），尽管接受率高达 69.9%。
   根因：**草稿参数量是 target 的 35%**（0.6B vs 1.7B），草稿开销吃掉全部收益。
   → 换成 7B/70B 这种更贵的 target，结论可能反转。
2. **接受率高 ≠ 快**：`draft-k3` 的 α（69.9%）高于 `draft-k8`（56.6%），速度却更慢。
   决定收益的是「每轮产出 ÷ 每轮成本」，只看接受率会得出完全错误的结论。
3. **零成本的 n-gram 草稿才是赢家**：草稿来自查表、几乎没有前向开销，
   所以同样的接受率下能实打实变成 1.83× / 1.19×。**先试 ngram，再考虑草稿模型。**
4. **理论模型只有定性价值**：`(1-α^(k+1))/(1-α) ÷ (k×ratio+1)` 对 k=3 预测 1.23×、实测 0.70×。
   它漏掉了每轮的固定开销（草稿前向、验证调度），**结论必须来自实测**。

**正确性验证（带自身重复性对照）**：基线 `base2` 与 `base` **12/12 逐字相同**，
说明服务端本身完全可复现；但开启投机解码后输出出现浮点级分叉
（draft 方案仅 1~3/12 与基线一致，ngram 11/12）。
→ **"投机解码无损"指的是分布无损，不是逐字可复现**——把「逐 token 前向」换成「k 个 token 批量验证」，
浮点累加顺序变了，贪心解码在并列位置可能翻转。

**四个工程前提（踩坑换来的）**：① 必须 `-np 1`（投机解码只支持单序列，Ollama 的构建默认 4 路）；
② 必须显式 `--spec-type draft-simple`（Ollama 的构建默认实现列表为空）；
③ CUDA 后端 DLL 的依赖要手工装配（`GGML_BACKEND_PATH` 指向 DLL + 目录进 `PATH`）；
④ Ollama 的 blob 就是标准 GGUF，可直接给 llama.cpp 用，省掉几 GB 下载。

### 实验 5 · 并发压测（httpx + asyncio，**流式**实测 TTFT）

| 并发 | QPS | 聚合 tok/s | TTFT P50 | TTFT P95 | P95 | P99 |
|---|---|---|---|---|---|---|
| 1 | 2.36 | 150.9 | **27.4 ms** | 40.7 ms | 443.8 ms | 445.8 ms |
| 2 | 2.42 | 154.3 | 434.6 ms | 448.0 ms | 860.4 ms | 874.4 ms |
| 4 | 2.48 | 157.7 | 1216.8 ms | 1298.3 ms | 1706.7 ms | 1715.2 ms |
| 8 | 2.51 | 160.2 | 2790.3 ms | 2813.9 ms | 3192.0 ms | 3194.1 ms |
| 16 | 2.47 | 157.3 | **4711.4 ms** | 6112.1 ms | 6517.6 ms | 6529.7 ms |

**结论：加并发只换到排队，换不到吞吐。**

- 并发 1 → 8，**QPS 只涨 6%**（2.36 → 2.51），但 **TTFT P95 涨了 69 倍**（40.7 → 2813.9 ms）。
- TTFT 随并发**线性增长**（27 → 435 → 1217 → 2790 → 4711 ms），是教科书级的 FIFO 排队特征。
- **根因**：Ollama 的 `OLLAMA_NUM_PARALLEL` 默认是 **1**，所有请求挤在**同一个 slot** 上串行执行
  （日志里只有 `slot id 0`）。并发度只影响排队长度，不影响吞吐。
- **工程含义**：优化的正确方向不是"扩并发"，而是**降低单请求成本**（更低的量化档 / 更短的上下文 /
  更少的输出 token）——这三项同时改善吞吐与延迟。若确实要提并发承载，
  需要设 `OLLAMA_NUM_PARALLEL>1` 并重启 Ollama（代价是每路并行各占一份 KV cache 显存）。

### 实验 5 补充 · 开启并行度后的验证（完整的"发现问题 → 归因 → 改进 → 验证"闭环）

实验 5 发现"加并发不涨吞吐"，根因是 `OLLAMA_NUM_PARALLEL=1`（请求在单 slot 排队）。
于是在**独立端口**起了一个 `OLLAMA_NUM_PARALLEL=4` 的实例做对照
（`--host` 指向它，主实例不受影响）：

| 并发 | P=1 QPS | P=4 QPS | 吞吐变化 | P=1 TTFT P50 | P=4 TTFT P50 | TTFT 变化 |
|---|---|---|---|---|---|---|
| 1 | 2.36 | 2.24 | ≈0.95× | 27.4 ms | 25.6 ms | ≈0.93× |
| 2 | 2.42 | **4.01** | **↑1.66×** | 434.6 ms | **34.9 ms** | **↓0.08×** |
| 4 | 2.48 | **6.09** | **↑2.46×** | 1216.8 ms | **51.9 ms** | **↓0.04×** |
| 8 | 2.51 | **6.27** | **↑2.50×** | 2790.3 ms | **676.6 ms** | **↓0.24×** |
| 16 | 2.47 | 6.18 | ↑2.50× | 4711.4 ms | 1641.9 ms | ↓0.35× |

**结论：同一个硬件、同一个模型，只改一个并行度配置，吞吐就翻 2.5 倍、首 Token 延迟降 12~24 倍。**

三个值得记的点：

1. **机制被数据钉死了**：QPS 在**并发 4 处饱和到 ~6.2**——正好等于并行 slot 数（4）。
   印证了"瓶颈是单 slot 串行执行"这个归因，而不是猜测。
2. **代价是显存**：模型占用 1.59 GB → **2.95 GB（+86%）**——每路并行各占一份 KV cache。
   8GB 卡上开 4 路并行后，能装的模型就要小一档，这是一个真实的取舍。
3. **低并发时没有副作用**：并发 1 时 QPS / TTFT 与基线基本一致（0.95×）。

> 复现：
> ```powershell
> # 1) 另起一个实例（不碰你本机的 Ollama）
> $env:OLLAMA_NUM_PARALLEL="4"; $env:OLLAMA_HOST="127.0.0.1:11440"; ollama serve
> # 2) 指向它压测，并与基线对比
> python -m inferbench load --host http://127.0.0.1:11440 --num-parallel 4 `
>     --levels 1,2,4,8,16 --requests 24 --compare results/load_full.json --tag parallel4
> ```
> 注意 `--num-parallel` 必须**显式声明**：服务器端的并行度客户端探测不到（第一版报告里标成了 1，是错的）。

这条结论对 SLO 的直接价值：**若要求 TTFT P95 < 200 ms，这个实例只能承载 1 路并发请求**——
按这个反推容量，而不是拍脑袋定副本数。

## 7. 踩坑记录（比结论更值钱的部分）

1. **多模型争抢显存 → 解码掉 286 倍**
   Ollama 默认让最近用过的模型常驻显存（`keep_alive`）。连着跑多档量化时，
   显存被打满（实测 7836/8188 MiB），推理退到 CPU/共享内存，
   **解码从 168 tok/s 掉到 0.59 tok/s**。
   现在每次测量前 `unload_all()` 清空显存、记录 GPU 基线，
   并用 `size_vram / size` 校验模型确实 100% 在 GPU 上。
2. **冷启动陷阱**：首次调用含 14s 模型加载，首调用 12 tok/s vs 预热后 168 tok/s。
   不预热，测出来的是加载时间。
3. **`/api/generate` 的模板坑**：同一句"什么是量化"，
   `/api/generate` 回成了"您好！请问有什么可以帮助您的？"，`/api/chat` 才稳定。
4. **`/api/ps` 不返回 `processor` 字段**（那是 CLI 自己算的），
   所以分流比例必须用 `size_vram / size` 自己算。
5. **embedding 模型的默认上下文也会吃爆显存**：`qwen3-embedding:0.6b` 默认 `num_ctx=32768`，
   KV cache 把 0.6GB 的模型撑成 **5.8 GB**，8GB 显存直接被顶满。
   单句 query 给 `num_ctx=512` 就够（`config.EMBED_NUM_CTX`）。
6. **预热必须用请求流中不存在的文本**：第一版把预热调用打在了 `stream[0]["text"]` 上，
   结果那条请求的"延迟"变成了模型冷加载的 8 秒，未命中 P95 被污染成 **8182 ms**（真实值约 150 ms）。
7. **绝对不要强杀正在进行的 `ollama pull`**：本项目踩过这个坑——
   为了读下载进度连续 3 次 `Stop-Process -Force`，分片写到一半被打断，
   续传时 Ollama 把残缺分片当成完整分片，最后 **`digest mismatch`，3.7GB 全部作废**。
   想读进度就让 pull 在前台跑（它自己会打印 `3.5 GB/4.1 GB 1.5 MB/s`），
   或者用 `-RedirectStandardError` 重定向到文件后读文件，**不要杀进程**。
